Part 1 · Environments

Rules for deployed URLs

Always
  • On preview URLs, do not add to cart, favorite, review, or edit anything. Every write lands in production.
  • On production, sign in only with the dedicated QA account. Never use a personal card.
  • Clean up anything you create on production the same day, and confirm the cleanup.
  • Admin uploads hit shared storage even from local. Delete test images and PDFs after use.

Part 2 · Local setup

Two extra steps most people miss

Make yourself an admin

Sign up once locally, then set your roleId to ADMIN.

npx prisma studio
# User → your row → roleId = ADMIN

Forward Stripe webhooks

Without this, every local checkout stays "pending".

stripe login
stripe listen --forward-to \
  localhost:3000/api/stripe/webhook
# whsec_… → STRIPE_WEBHOOK_SECRET
# then restart npm run dev

Part 2 · Payment QA policy

The QA promo code must be safe to leak

The app accepts only public codes, and the Stripe account is shared with pacemaker-apply. Every QA code must:

  • be a long random string
  • allow 1 redemption
  • expire within an hour
  • be deactivated right after the test
Refunds

Today a Stripe refund does not change the order or remove access. A fix is open in PR #1162. Until it ships, every refund needs a manual DB correction.

Part 3 · The rule that shapes our process

Merge is release.

Nothing sits between a merge to main and production. QA sign-off happens before merge, never after.

Part 3 · QA process

Acceptance criteria you can test

Given a signed-in member who already owns the ebook
When they open the ebook detail page
Then the button reads "Purchased"
And clicking it shows the already-owned modal
    without adding to cart

The same sentences become the names of automated tests.

Part 3 · QA process

Recurring work

Before risky releases

Payments, access rules, or schema changed: run the full regression checklist. Small UI change: check the affected flow.

One escaped bug, one new test

Every bug found in production gets an automated test that would have caught it.

Exploratory sessions

Weekly, 30 to 60 minutes, one goal, no script. Example: "break promo codes". Log what you tried.

Monthly review

For each bug that reached production, note why QA missed it and update the checklist.

Part 3 · For the team to decide

Two process changes to agree on

Require QA approval before merge

For PRs that change screens, payments, or access. GitHub branch protection can enforce a required reviewer.

Create a real staging environment

Give preview deployments their own database and a Stripe test key. Pre-release checks then move off production.
