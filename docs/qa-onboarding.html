The product

Pacemaker Video sells career-development content to job seekers: resume, interview, and networking skills, plus industry-specific material. Members browse, save favorites, buy through a cart, and then watch, read, or attend what they bought. Admins manage the catalog.

What is for sale

ProductWhat the member getsPublic URLDB ItemType
CourseA video course split into sections and lessons, played with Wistia. Watch progress is tracked./coursesCOURSE, VIDEO
EbookA PDF read in the in-app viewer. Some ebooks are public, others need a purchase./ebooksEBOOK
WorkshopA live session. Status is Open, Closed, Completed, or Hidden. Buying one enrolls the member./workshopsWORKSHOP

Prices are charged in Canadian dollars (CAD).

Rules for deployed URLs
  • On preview URLs, do not add to cart, favorite, review, or edit anything. Every write lands in the production database.
  • On production, sign in only with the dedicated QA account. Never use a personal card.
  • Anything you create on production gets cleaned up the same day, and you confirm the cleanup.
  • Admin uploads go to shared storage even from local. Delete test images and PDFs after use.

Local setup

You need nvm, Docker, and the Stripe CLI. Node version comes from .nvmrc (22.22).

1. Install and configure

nvm install && nvm use
npm install
cp .env.local.example .env.local   # ask the team for local values

Use test keys only in .env.local: Clerk pk_test_… / sk_test_… and Stripe sk_test_…. Never copy production values into your machine.

2. Start the database and seed it

docker compose up -d          # Postgres on localhost:5433
npx prisma migrate dev
npx prisma db seed            # sample courses, ebooks, workshops, banners, roles

To reset to a clean state, run npx prisma migrate reset. It drops all local data and re-seeds.

3. Run the app

npm run dev                   # http://localhost:3000
npm run dev -- -p 3001        # or 3001, the port the team's Aside session uses

Open the app at localhost, not 127.0.0.1. Clerk sessions break on the IP address. Keep NEXT_PUBLIC_APP_URL in sync with the port, because Stripe redirects back to it.

4. Make yourself an admin

Sign up once in the local app. Your user row is created on first sign-in. Then open Prisma Studio and set your roleId to ADMIN.

npx prisma studio             # User table → your row → roleId = ADMIN

5. Connect Stripe webhooks

Without this step, every local checkout stays at "Payment confirmation pending", because the order is only marked complete when Stripe calls the webhook.

stripe login
stripe listen --print-secret   # put this whsec_… in .env.local as STRIPE_WEBHOOK_SECRET (once per machine)
stripe listen --forward-to localhost:3000/api/stripe/webhook \
  --events checkout.session.completed,charge.refunded
# restart npm run dev after changing .env.local; use :3001 if you run there

The Stripe checkout page shows a Sandbox label in test mode. If it is missing, stop: your local key is a live key.

Critical flows

These are the flows that cost money or trust when they break. Each one lists the normal path and the edge cases that have broken before or are easy to miss. Run them locally.

Add to cart

The ebook version below comes from the team's testing routine. Use the same four states for courses and workshops.

StateActionExpected
Signed outClick "Add to Cart"Sign-in required modal; confirm goes to /sign-in.
Signed inClick "Add to Cart"Item added with the right type; confirmation modal.
Already in cartOpen detail pageButton reads "Go to Cart" and opens /mypage/cart.
Already ownedClick the buttonButton reads "Purchased"; modal says it is already owned; cart unchanged.

Checkout

ScenarioExpected
Card succeedsRedirect to payment success; status Complete; cart emptied; item appears in purchases.
Card declinedStripe shows the error; no completed order; cart intact.
3-D Secure requiredChallenge appears; passing it completes the order; failing it does not.
Cancel on StripeReturn to /payment/cancel; cart intact. A PENDING order remains in the DB by design.
Webhook not receivedSuccess page shows "Payment confirmation pending" and does not grant access.
Item already ownedCheckout refuses to charge for it again.
Full refundOrder becomes REFUNDED; course and ebook access is gone; workshop seat is removed; the member can buy again.
Partial refundNothing changes for the member. The order stays COMPLETED and the server logs it for manual follow-up.
Repeated refund eventNo change on the second delivery.

Trigger a local refund from the Stripe test dashboard, or with stripe refunds create --payment-intent pi_….

After purchase

  • Course: the player in /mypage/purchases/[videoId] loads every lesson; watch progress survives a reload.
  • Ebook: the full PDF opens; a non-buyer still sees only what is public.
  • Workshop: the member is enrolled and the purchase shows in history.
  • Access gating: sign in as a different member and confirm the same URLs are refused.

Payment QA policy

Production charges real cards. This is how far you may go in each place.

WhereAllowedHowCleanup
LocalEverythingTest key, test cards, Stripe CLI webhooks. Automated tests run here.Reset the local DB.
PreviewNothingNo Stripe key is configured, and writes hit the production DB.None needed.
Production, every releaseOpen checkout, then cancelConfirms the live Stripe page opens and the cancel page returns.Delete the PENDING order.
Production, every releaseOne free purchaseQA account plus a one-time 100% promo code. See below.Delete the order, order items, and any workshop enrollment.
Production, exceptionalOne real card paymentOnly for a first launch or a large payment change, with sign-off from the owner. Smallest price, company card, refund right away.Full refund in Stripe, then confirm the order shows Refunded and access is gone.

Rules for the QA promo code

The app accepts only public promotion codes, and the Stripe account is shared with pacemaker-apply. A leaked 100% code would work on both sites. So every QA code must:

  • be a long random string, never a word like QATEST;
  • have a redemption limit of 1;
  • expire within one hour;
  • be deactivated right after the test, even if it went unused.
Refunds

The webhook handles checkout.session.completed and charge.refunded. A full refund marks the order Refunded and removes access. A partial refund changes nothing in the app; it is logged and needs manual follow-up. Events from other apps on the shared Stripe account are acknowledged and ignored.

Browser testing rules

  • Aside is the default browser for local e2e. Keep a signed-in session on localhost:3001.
  • Use Chrome only when you need a real profile, cookies, or SSO state.
  • Before a signed-in test, note what is already in the account's cart, orders, and favorites.
  • After the test, remove what you created and confirm the account is back to where it started.
  • If you could not run a check, say so and name the risk. Never report it as passed.

Automation

You own test automation. Today the repo has about 40 Vitest files and no browser e2e suite. The biggest gains are in the flows above.

Unit and component tests

Tests sit next to the code they cover as *.test.ts or *.test.tsx, or in a nearby __tests__ folder. Good examples to read first:

  • src/app/api/stripe/webhook/checkout-webhook-flow.test.ts for payment logic
  • src/app/ebooks/[ebookId]/page.test.tsx for page states
  • src/app/admin/admin-actions-auth.test.ts for permission checks
npx vitest run src/lib/__tests__/stripe-fulfillment.test.ts   # one file
npx vitest                                                     # watch mode

Browser e2e: proposed direction

This is a proposal. Agree on it with the team before adding dependencies.

Local suite

  • Playwright in an e2e/ folder
  • Runs against localhost with a freshly seeded DB
  • Clerk test users for signed-in flows
  • Stripe test cards and Stripe CLI webhooks
  • Covers every flow in Critical flows

Production smoke

  • Read-only: pages load, catalog renders, sign-in page opens
  • No cart, checkout, favorites, or reviews
  • No credentials stored in the repo
  • Free-purchase check stays manual

Suggested order: checkout with webhook, cart states, access gating after purchase, admin permission checks, then admin content editing.

Team workflow

How a change moves from ticket to production, and where QA steps in.

  1. Jira ticketWork starts from a PACE- ticket. npm run jira is a local CLI for it.
  2. BranchNamed PACE-123/short-description, or chore/… and hotfix/…. A pre-commit hook rejects other names and runs type check and lint on staged files.
  3. Pull requestThe template asks for Why, Changes, and How to Test.
  4. QA on the branch QACheck out the branch, run it locally, follow How to Test, then probe the edge cases it does not mention.
  5. CI and reviewLint, schema sync, build, tests. A reviewer approves.
  6. Merge to mainCI applies database migrations to production, and Vercel deploys production.
  7. Production smoke QAShort controlled checks from the payment policy, with same-day cleanup.
Migrations

Merging a PR that changes prisma/schema.prisma changes the production database immediately. Test those PRs locally with npx prisma migrate reset and real-looking data before approving.

QA process

How QA runs once you are set up. There is no single mandatory standard, but most teams share four habits: test the riskiest areas first, join work at the ticket stage, automate in a pyramid, and repeat the same checklist at every release.

Merge is release

A merge to main deploys production and runs migrations right away. There is no step between merge and release where QA can stop a change. QA sign-off therefore happens before merge, never after.

First two weeks: map the risk

  • Build a risk map. Score each feature on impact if it breaks and on how often it changes. Payments, post-purchase access, and admin permissions start at the top.
  • Map existing coverage. Mark which risks the current Vitest files already guard. High risk with no test is your first automation target.
  • Write regression checklist v1. Start from Critical flows. This is the list you rerun before risky releases.

Every ticket: the core loop

WhenWhat QA doesOutput
Ticket is writtenCo-write acceptance criteria in Given / When / Then form.Criteria on the Jira ticket
PR is openedRun the branch locally. Follow "How to Test", then probe the edge cases it does not mention.A "Verified" PR comment listing what was and was not checked
A problem is foundReport it with the template and set severity.Jira bug
Right after mergeRun the production smoke from the payment policy.Smoke result and cleanup confirmation

Example acceptance criteria:

Given a signed-in member who already owns the ebook
When they open the ebook detail page
Then the button reads "Purchased"
And clicking it shows the already-owned modal without adding to cart

Recurring work

  • Before risky releases: if a PR touches payments, access rules, or the schema, run the full regression checklist. For small UI changes, check only the affected flow.
  • One escaped bug, one new test: every bug found in production gets an automated test that would have caught it.
  • Exploratory sessions: once or twice a week, spend 30 to 60 minutes on one focused goal without a script, for example "break promo codes". Write down what you tried and what you found.
  • Monthly review: for each bug that reached production, note why QA missed it and adjust the checklist.

Process changes to agree on

  • Require QA approval before merge for PRs that change screens, payments, or access. GitHub branch protection can enforce a required reviewer.
  • Create a real staging environment. Point preview deployments at their own database and a Stripe test key. Pre-release checks then move off production.

Glossary

Webhook
A call Stripe or Clerk makes to our app when something happens on their side, such as a completed payment.
Stripe Checkout
Stripe's hosted payment page. The member leaves our site to pay and is sent back afterwards.
Live key / test key
Stripe credentials. A live key charges real money; a test key accepts only test cards.
Promotion code
A discount code a member types at checkout, backed by a Stripe coupon.
Preview deployment
A temporary Vercel URL built for a branch or PR. Here it shares production data.
Migration
A versioned change to the database structure, stored in prisma/migrations.
Seed
Sample data loaded into a fresh local database by prisma/seed.ts.
Entitlement
The rule that decides whether a member may open a course, ebook, or workshop. See src/lib/entitlements.ts.
Commit gate
The four checks every change must pass before it is called ready.
Aside
The browser automation tool the team uses for local e2e with a saved sign-in.
